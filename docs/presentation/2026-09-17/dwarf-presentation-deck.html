Cardano-node + Amaru

DWARF

Adversarial testing against real node implementations, with reproducible scenarios and evidence that survives the run.

Open with the result, not the implementation history. DWARF runs real Cardano-node and Amaru software, puts controlled workloads and faults around them, and retains enough evidence to decide whether a signal belongs to a node, the harness, or the platform. Today I will show the deployed product, every current operator surface, a live mixed-node run, what the evidence supports, what remains untested, and the operating decisions needed to use it routinely.

01 · Security objective

The infrastructure security objective

Identify vulnerabilities before malicious actors can exploit them.

Establish whether Cardano-node and Amaru remain safe, compatible, and recoverable under adversarial inputs, peers, infrastructure faults, and state transitions.
Maintain an evidence-backed catalog of risk affecting Cardano infrastructure and its Haskell and Rust node implementations.
Provide repeatable insight into the security posture of Cardano's node and protocol infrastructure.
  • Real implementationsExercise real node software through real interfaces. Avoid simulated nodes and emulated consensus.
  • Missing capabilityThe current Cardano and Amaru testing stack has no other tool combining mixed real-node execution, generative adversarial testing, infrastructure faults, and retained evidence.
  • Complex ownershipIndependent implementations, teams, repositories, releases, operators, and deployments share the same protocol.
  • High consequenceFailures can affect availability, consensus, interoperability, or ledger integrity. Remediation often crosses teams and releases.
  • Memory-safe foundationsHaskell and Rust reduce classic memory-corruption exposure. Risk remains in protocol state, logic, resource handling, integration, lifecycle, and recovery.
Infrastructure scopeNode and protocol infrastructure: N2N peer protocols; N2C local-client interfaces; serialization and validation; consensus, chain selection, and transaction or block processing; persistence, bootstrap, and recovery; resource handling, configuration, and deployment.
Outside this audit scopeIndividual Plutus scripts or smart contracts, dApps, wallets, bridges, exchanges, and application-specific off-chain systems.
This project focuses below the application layer. N2C denotes local-client interfaces; the processing and lifecycle layers that follow are not subparts of N2N. DWARF can exercise the node's Plutus and ledger-validation machinery, but it does not audit individual contracts or dApps. Haskell and Rust provide strong memory-safety defaults, with normal caveats around unsafe code and foreign interfaces. The security problem shifts toward protocol logic, cross-implementation compatibility, resource handling, lifecycle behavior, and recovery. The novelty statement is deliberately bounded to the current Cardano and Amaru testing stack.

12 · Object model

Five objects turn test intent into reproducible evidence

01 · Target

What runs

A real implementation, binary or image, input contract, revision, outcomes, and invariants.

02 · Profile

How it is arranged

Reusable node counts, topology, network parameters, and shared environment choices.

03 · Scenario

What happens

Pinned intent: runtime, seed, phases, workload, faults, probes, assertions, and teardown.

04 · Primitive

How each step executes

A registered, schema-checked operation with declared runtime and target support.

05 · Run

What happened

Resolved inputs, events, outputs, assertion evidence, logs, status, and exportable evidence.

Catalog objects are reusable definitions. A run resolves them into one immutable, inspectable execution record.

Use this vocabulary once, then reuse it throughout the walkthrough. A target manifest identifies the executable boundary. A profile describes the reusable network arrangement. A scenario composes registered primitives into ordered phases. The run records the resolved combination and its evidence. A verified portable bundle is one export form, not a synonym for every historical run record. This separation is why the same scenario can be reused against pinned target revisions without hiding what changed.

17 · Engine stack

Valid seeds, four search mechanisms, one evidence path

Cuddle / CDDL · upstream seed source

DWARF's offline generator runs Cuddle against the official CDDL and writes structurally valid Cardano CBOR into its generated corpus. With --wire, the same tool non-destructively populates the applicable AFL++ and cargo-fuzz seed corpora. No manual file copying is required. Cuddle supplies structural starting material, not semantic validity or runtime fuzzing; the stateful N2N generator uses separate embedded protocol models.

Coverage-guided native

AFL++

Mutates seed corpora against compiled, instrumented native harnesses and retains queue, coverage, crash, and hang telemetry.

Coverage-guided Rust

cargo-fuzz / libFuzzer

Uses Rust compiler instrumentation for Amaru and Pallas decoder surfaces, with corpus growth and replayable crash inputs.

Fast CI regression gate

Bounded CI mutator

Feeds deterministic structural anchors and random bytes to compiled decoder harnesses. It has no coverage feedback and is not AFL++.

Live protocol behavior

Stateful N2N protocol generator

Creates seeded illegal ChainSync, BlockFetch, TxSubmission2, and KeepAlive sequences over real N2N sessions.

TargetsCompiled harnesses or live Cardano-node and Amaru processes
OraclesAccept/reject/crash plus reachability, containment, liveness, recovery, and differential behavior
EvidenceSeed, exact input, coverage or protocol cells, logs, assertions, provenance, and replay bundle
Cuddle is shown above the engines because it is an upstream, specification-derived seed source. Its position does not mean every scenario starts with Cuddle or that Cuddle ranks above the search engines. DWARF's supplied generator performs the corpus handling: --wire generates and populates applicable AFL++ and cargo-fuzz corpora, while --wire-only rewires already generated seeds. Phase 1 was prototyped with Cuddle 1.8.1.1 and retained the pre-existing hand seeds. Mini-protocol CDDL wrapping and deep replacement of hand-written shapes remain open, so do not imply that Cuddle supplies the stateful N2N generator today. AFL++ and cargo-fuzz/libFuzzer are the coverage-guided campaign engines. The current GitHub Actions library-fuzz workflow instead uses a lightweight deterministic Python mutator for fast regression detection. The stateful N2N generator performs behavioral exploration through real mini-protocol sessions rather than victim-node edge coverage. 22 · Proposal

Scope recommendation

DWARF's primary purpose is security testing

DWARF was built to identify, reproduce, and classify security failures in real Cardano-node and Amaru implementations. That should remain its focus.

  • Security firstExercise hostile inputs, peers, infrastructure faults, and state transitions. Prove containment, recovery, and cross-implementation behavior.
  • Useful beyond securityThe same real-node orchestration can support correctness, compatibility, performance, and operational analysis when needed.
  • Complement existing toolsSpecialized tools already cover routine benchmarking, conformance, release validation, and fleet monitoring. DWARF can use their outputs when they strengthen security evidence.
The recommendation is to keep DWARF centered on security. Its real-node orchestration and evidence machinery can support adjacent engineering questions, but capability alone does not justify turning DWARF into a general benchmark suite, conformance framework, release system, or production monitoring stack. Existing specialist tools should continue to own those routine functions. DWARF can consume or cite their outputs when they help prove, classify, or reproduce a security result.

23 · Proposal

Client decision

Two levels of node measurement

Option 1

Security regression measurements

The closest useful answer with modest engineering and maintenance cost.

Evidence

Pinned stock nodes, complete DWARF protocol transcripts, existing Cardano tracing and Amaru telemetry, plus independent chain observation.

Answers

Release deltas for transfer, throughput, goodput, block or transaction adoption, restart, sync, epoch behavior, and recovery under clean and hostile conditions.

Limit

Reports end-to-end and node-emitted timing. It cannot separate hidden decode, validation, queue, lock, or execution stages.

Option 2

Selective native instrumentation

Adds exact internal attribution where the client needs it most.

Evidence

Everything in Option 1, plus bounded counters, histograms, or spans inside real Cardano-node and Amaru builds at agreed event boundaries.

Answers

Selected mini-protocol and node-stage timing such as receive, decode, validate, apply, adopt, VM execution, and queue delay.

Tradeoff

Requires paired stock and instrumented runs, overhead calibration, pinned patch sets, and upkeep as both implementations change.

Present these as two credible investment levels, not as current DWARF functionality or fixed delivery commitments. Option 1 uses real stock nodes. A complete protocol transcript proves what DWARF sent and received, while existing node telemetry and an independent observer establish the node-emitted and final outcomes that are actually visible. It gives useful release comparisons without pretending to know time spent inside unexposed functions. Option 2 still runs real nodes rather than simulations. It adds bounded observational events through each implementation's native tracing system, then compares the instrumented build with a stock build from the same revision to measure observer overhead. DWARF would version and retain each measurement definition, scenario, telemetry adapter, optional instrumentation patch, build recipe, and accepted baseline so later releases can reuse the same test.
